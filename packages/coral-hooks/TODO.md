# Coral Hooks 실험 TODO

## 목적

Coral이 React 훅과 해당 훅을 사용하는 JSX Parts를 함께 제공할 수 있는지 실제
구현으로 검증한다. 훅은 상태, 접근성 속성, 이벤트, Ref와 DOM 생명주기 동작을
소유하고, JSX Parts는 같은 훅의 결과를 기본 HTML 요소에 연결한다.

사용처는 JSX Parts로 기본 연결을 제공받거나, 훅으로 HTML 구조와 연결을 직접
구성할 수 있어야 한다. 두 사용 방식에서 행동을 별도로 구현하지 않는다.
`useTabs`와 `getTabProps()` 같은 이름과 API 형태는 검토할 예시이며 확정된 계약은
아니다.

## 작업 경계

- 이 문서는 별도 세션에서 진행할 구현 실험의 작업 지시서다. 2026-10-27에
  대표 패턴의 구현과 검증을 완료했다. 결과와 한계는 `README.md`, 설계 선택은
  `Question.md`에 기록했다.
- 작업 범위는 `packages/coral-hooks`와 실험 실행에 꼭 필요한 워크스페이스 설정으로
  한정한다. 기존 Coral을 교체하거나 공개 API를 변경하지 않는다.
- 시작 시 작업 트리를 확인하고, 다른 세션과 사용자가 만든 변경을 보존한다.
  특히 기존 Coral의 진행 중인 Tabs 구현을 덮어쓰지 않는다.
- 기존 Coral 구현을 비교 기준으로 사용한다. 훅의 JSX 사용 가능성과 실제 사용자
  동작을 확인하기 전에 공통 추상화나 모든 컴포넌트의 일괄 이전을 진행하지 않는다.
- 설계 결정이 필요하면 사용자에게 묻지 않고 실험에 필요한 선택을 내린다. 질문,
  선택지, 선택 결과와 근거는 이 디렉터리의 `Question.md`에 기록한다.
- 문서와 결과 보고는 한국어로 작성한다. 테스트 파일은 저장소의 보존 규칙을 따른다.
  임시 검증 파일은 검증 후 제거하고, 기존 파일과 다른 사람이 만든 파일은 보존한다.

## 2. 훅과 JSX Parts의 공동 구현

- [x] 훅을 직접 사용하는 HTML 예제와 같은 훅을 사용하는 JSX Parts 예제를 만든다.
- [x] 상태, 이벤트, 접근성 속성과 DOM 동작의 구현을 훅이 소유하도록 구성한다.
      JSX Parts에는 기본 요소 선택, Props 연결과 필요한 Context 공유를 둔다.
- [x] 제어·비제어 상태, 초기값, 변경 통지와 변경 취소 중 각 패턴에 필요한 계약을
      정하고 두 사용 방식에서 같은 결과를 제공한다.
- [x] 사용자 Props, 이벤트와 Ref를 내부 동작과 안전하게 합성하는 방법을 구현한다.
      필요한 Props나 Ref를 누락하거나 덮어썼을 때의 보장 범위도 문서에 명시한다.
- [x] 한 패턴을 여러 번 사용하거나 중첩하고, 항목을 추가·제거·재배치하는 경우에
      인스턴스의 상태와 DOM 참조가 섞이지 않는지 확인한다.
- [x] JSX Parts가 직접 사용하는 훅과 사용처에 공개하는 훅이 같은 동작을 제공하는지
      확인한다. 불필요한 별도 Machine·Actor·Adapter 계층을 도입하지 않는다.

## 3. 대표 패턴의 구현 실험

대표 패턴으로 실제 구현 가능성을 확인한 후, 나머지 컴포넌트는 조사 결과를 바탕으로
적용 가능성과 추가 실험이 필요한 부분을 정리한다. 모든 컴포넌트의 구현을 완료해야
하는 실험으로 범위를 늘리지 않는다.

- [x] Tabs를 구현한다. 선택 상태, 자동·수동 활성화, 방향키와 Home/End 이동,
      수평·수직 방향, RTL, disabled, 패널 표시와 ID 참조를 검증한다.
- [x] ToggleGroup을 구현한다. 단일·다중 선택, 선택과 포커스의 구분, 키보드 이동,
      disabled와 변경 취소를 검증한다.
- [x] Checkbox를 구현한다. 네이티브 입력과 대체 요소를 비교하여 선택·혼합 상태,
      Space 활성화, Label 연결, disabled와 Form 동작을 검증한다.
- [x] Slider를 구현한다. 네이티브 range 입력과 대체 요소를 비교하여 키보드,
      포인터·터치, 값의 범위, 다중 값, disabled와 Form 동작을 검증한다.
- [x] Button을 조사한다. 네이티브 `<button>`만으로 충분한 경우와 대체 요소에서
      추가 구현이 필요한 경우를 비교한다. `useButton`을 제공할 실익과 지원 요소의
      범위를 결정하고, 필요하면 최소 구현으로 검증한다.
- [x] 나머지 Coral 컴포넌트의 적용 가능성, 네이티브 요소 제한, DOM 생명주기 의존성과
      미검증 항목을 정리한다. 아직 구현하지 않은 복잡한 패턴의 가능성을 검증 완료로
      표시하지 않는다.

## 4. 네이티브 HTML과 대체 요소의 경계

`role`은 네이티브 요소의 키보드, 포커스, disabled와 Form 동작을 대신 구현하지
않는다. 대체 요소를 지원한다고 선언한 경우에는 사용자가 경험하는 결과를 실제로
구현하고 검증한다.

- [x] 네이티브 요소와 대체 요소 각각에 필요한 키보드 입력, 클릭 생성, 포커스와
      disabled 처리를 정의한다. 이벤트가 중복으로 처리되는 경우도 확인한다.
- [x] Form 제출 값, reset, required, 유효성 검사, Label 클릭과 fieldset의 disabled
      전파 중 지원할 계약을 정하고 실제 브라우저에서 확인한다.
- [x] HiddenInput 같은 네이티브 보조 요소가 필요한지 확인한다. 사용하는 경우에는
      접근성 트리와 Tab 순서에 중복된 컨트롤이 생기지 않는지 검증한다.
- [x] 네이티브 요소를 유지하는 것이 더 적합한 Part는 지원 요소와 필수 속성을
      명시하고, 대체 요소를 제한한 이유를 기록한다. 훅 API가 임의의 태그 지원을
      자동으로 뜻한다고 가정하지 않는다.
- [x] 요소가 변경되거나 제거될 때 Ref 갱신, 포커스 복구, 이벤트·Observer 정리와
      React Strict Mode의 재실행을 확인한다.

## 5. ID와 SSR 계약

- [x] 기본 ID 생성, 사용자 지정 ID와 요소 간 참조의 소유자를 결정한다. Root의
      ID 재정의 API, Part 등록과 사용처의 명시적 연결을 비교하고 선택을 기록한다.
- [x] 기본 사용법에서 반복적인 수동 ARIA 연결을 얼마나 요구하는지 평가한다.
      Tabs의 매 쌍에 네 개의 ID·참조 속성을 지정하는 방식은 사용 부담이 크다는
      사용자 의견을 반영한다.
- [x] 서버 HTML에 포함되는 관계와 hydration 또는 Effect 이후 완성되는 관계를
      구분한다. ID가 안정적인 것과 참조 관계가 처음부터 존재하는 것을 각각 확인한다.
- [x] Label·Panel의 생략, 조건부 렌더링, 사용자 지정 ID와 여러 인스턴스를 검증한다.
      존재하지 않는 ID 참조와 hydration 불일치도 확인한다.
- [x] Meter·Progress의 명시적 이름 연결에 관한 Journey는 해당 컴포넌트의 결정임을
      고려한다. 다른 패턴에 적용할 정책은 이번 실험의 근거로 별도 판단한다.

## Question.md 작성 규칙

설계 질문이 생길 때마다 같은 파일에 항목을 추가한다. 구현 전에 선택을 기록하고,
검증 결과가 달라지면 같은 항목에 결과와 변경 이유를 보완한다.

- **질문과 배경:** 어떤 구현을 위해 결정이 필요한지 적는다.
- **선택지:** 실제 검토한 대안과 각 대안의 장점, 비용과 제한을 적는다.
- **선택:** 실험에서 선택한 방법과 그 근거를 적는다.
- **검증:** 선택을 확인한 코드, 예제, 실행 결과 또는 명세를 적는다.
- **한계와 재검토 조건:** 보장하지 못하는 동작과 이후 확인할 조건을 적는다.

확인하지 않은 내용을 사실로 기록하지 않는다. 실험용 선택을 프로젝트 전체의
확정된 정책으로 표현하지 않는다. 기존 Journey 파일은 수정하지 않는다.
