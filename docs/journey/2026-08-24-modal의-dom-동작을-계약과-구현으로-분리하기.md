# 2026-08-24 — Modal의 DOM 동작을 계약과 구현으로 분리하기

## 문제

WAI-ARIA APG의
[Dialog (Modal) 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)은
Dialog가 열릴 때 Focus를 내부로 옮기고, `Tab`과 `Shift+Tab`이 Dialog 밖으로
나가지 않게 하며, 닫힌 뒤에는 원칙적으로 호출한 요소로 Focus를 돌려보내도록
요구한다. 활성화된 동안에는 외부 콘텐츠도 조작할 수 없어야 한다. Bison이
`aria-modal="true"`를 반환하려면 이러한 동작이 실제로 성립한다는 보장이 함께
필요했다.

그러나 Focus Trap, Focus 복원, 외부 영역의 `inert` 처리와 Scroll Lock은 렌더링된
요소, Portal의 위치, Focus 가능한 자식과 Mount·Unmount 시점을 알아야 한다.
프레임워크에 독립적인 Machine이나 `connect`가 DOM을 직접 탐색하고 전역 Listener를
관리하면 React 같은 렌더러의 생명주기와 역할이 겹친다. 반대로 이 책임을 아무
계약 없이 컴포넌트에 넘기면 Modal의 필수 동작을 빠뜨린 구현도 Bison Dialog를
사용했다는 이유만으로 올바른 패턴처럼 보일 수 있었다.

## 접근 방식

첫 번째 방법은 Bison이 Focus와 외부 영역을 직접 조작하는 것이었다. 하나의
구현으로 동작을 강제할 수 있지만 Bison이 Element 참조, Portal, Event Listener와
정리 시점을 소유해야 한다. 이는 상태와 행동 계약을 Framework 생명주기에
연결하되 직접 DOM을 렌더링하거나 관리하지 않기로 한 기존 책임 경계와 충돌한다.

두 번째 방법은 Bison이 Role과 ARIA 속성만 제공하고 Focus Trap과 `inert`를
컴포넌트의 선택 사항으로 두는 것이었다. 구현은 단순해지지만 APG는 실제로 모든
사용자의 외부 상호작용을 막을 때에만 Dialog를 Modal로 표시해야 한다고 경고한다.
ARIA만 Modal이라고 선언하고 실제 동작이 그렇지 않으면 보조 기술 사용자는 외부
콘텐츠를 인식할 수 없으면서 다른 사용자는 외부와 상호작용할 수 있는 불일치가
생긴다.

세 번째 방법은 Bison이 Modal에 필요한 결과를 선언적인 행동 계약으로 제공하고,
DOM을 소유한 컴포넌트 계층이 이를 실행하는 것이었다. Bison은 어떤 조건에서 어떤
동작이 필요한지 계속 결정하므로 책임을 포기하지 않는다. 컴포넌트는 현재
Framework와 실제 DOM 구조에 맞춰 그 계약을 구현할 수 있다.

## 해결

Bison의 Dialog는 Modal이 활성화됐을 때 초기 Focus를 내부로 옮기고, Focus를
내부에 가두고, 닫힌 뒤 복원하며, 외부 영역을 `inert`하게 만들고 Scroll을
차단해야 한다는 계약을 API로 제공한다. `connect`는 Bison이 직접 소유할 수 있는
Dialog와 Trigger의 HTML·ARIA 속성, 열기·닫기와 `Escape` 입력을 제공한다.

실제 Focus 이동과 Trap, 복원, `inert`, Scroll Lock의 적용과 정리는 Dialog를
렌더링하는 컴포넌트 계층이 맡는다. 이 계층은 Portal과 렌더링된 Focus 대상 및
생명주기를 알고 있으므로 계약을 실제 DOM 동작으로 만들 수 있다. Bison과 Coral을
조합하는 상위 계층도 이 계약을 빠뜨리지 않고 연결해야 한다.

검증 책임도 같은 경계로 나눈다. Bison에서는 상태에 따라 Modal 계약과 직접
연결한 HTML·ARIA 및 키보드 결과가 올바른지 테스트한다. 계약을 소비하는
컴포넌트에서는 실제 브라우저로 Focus 이동·순환·복원과 외부 비활성화 및 Scroll
차단을 테스트한다. 상위 계층이 이 계약을 구현하지 않았다면 `aria-modal`만
있더라도 완성된 Dialog 패턴으로 보지 않는다.
