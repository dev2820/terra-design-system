# 2026-08-31 — Bison을 제거하고 접근성 책임을 Coral로 통합하기

## 문제

Bison은 WAI-ARIA APG 패턴마다 프레임워크에 독립적인 상태 머신 패키지를 두고,
`machine`이 전이를, `connect`가 HTML·ARIA 속성과 이벤트를 제공하는 계층으로
설계되었다. 이 구조는 행동을 표현과 분리하고 패턴별 접근성 계약을 한곳에서
검증하려는 목적에서 출발했다.

하지만 패턴을 순서대로 구현하면서 APG 패턴이라는 분류와 상태 머신이 필요한
문제의 범위가 일치하지 않는다는 점이 드러났다. Alert와 Breadcrumb에는 전이할
상태나 이벤트가 없었고, Button과 Checkbox의 핵심 키보드 동작은 네이티브 HTML이
이미 제공했다. Disclosure도 네이티브 Button과 펼침 상태를 직접 연결하는 것보다
별도 Machine·Actor·Connect 계층을 둘 때 더 많은 개념이 필요했다. 반대로 Dialog의
Focus 이동·순환·복원, 외부 영역 비활성화와 Scroll Lock처럼 실제로 어려운 동작은
렌더링된 DOM과 생명주기를 아는 컴포넌트가 구현해야 했고, Bison은 이를 선언적인
계약으로만 남겼다.

결과적으로 Bison은 단순한 패턴에는 필요하지 않은 상태 머신 형태를 강제하면서,
복잡한 패턴의 핵심 DOM 동작은 완성하지 못하는 중간 계층이 되었다. 아직 Bison을
사용하는 실제 제품이나 Coral 구현도 없어 이 계층을 유지해야 할 호환성 근거도
없었다. Link 패턴을 검토했을 때 네이티브 Anchor의 의미를 다시 포장하는 것 외에
Machine이 소유할 행동이 없다는 점은 이 불일치를 더 분명하게 보여주었다.

## 접근 방식

첫 번째 대안은 기존 방향을 유지하고 모든 APG 패턴을 Bison 패키지로 구현하는
것이었다. 패턴 목록과 패키지 목록이 일치해 진행 상황은 명확하지만, APG는
상태 머신 목록이 아니라 접근 가능한 UI를 만드는 지침이다. 상태가 없는 패턴에도
빈 Machine과 Connect를 만들고, 네이티브 동작을 별도 전이로 다시 표현해야 하므로
앞으로도 같은 과도한 추상화가 반복된다.

두 번째 대안은 Bison을 실제 상태 전이가 복잡한 패턴으로만 축소하는 것이었다.
불필요한 패키지는 줄일 수 있지만 어떤 복잡도부터 별도 행동 계층이 필요한지
증명할 실제 사용처가 아직 없다. 컴포넌트 하나의 지역 상태도 모두 독립 상태
머신으로 분리할 수 있어, 이름과 범위만 좁힌 채 기존 구조를 보존할 위험이 있었다.
현재의 Bison을 유지하는 직접적인 소비자도 없으므로 이미 만든 코드 자체는 이
계층을 계속 둘 근거가 되지 않는다고 판단했다.

세 번째 대안은 Bison을 제거하고 HTML 구조, 행동과 접근성을 실제로 렌더링하는
Coral 컴포넌트가 함께 소유하게 하는 것이었다. 이 방식에서는 Alert, Link,
Checkbox처럼 네이티브 HTML로 충분한 부분은 브라우저의 의미와 동작을 그대로
사용할 수 있다. Accordion, Carousel처럼 상태가 필요한 패턴은 컴포넌트가 필요한
상태만 지역적으로 소유하고, Dialog처럼 DOM 생명주기가 필요한 동작도 같은
계층에서 구현하고 실제 결과를 검증할 수 있다. APG는 계속 구현과 검증의 근거로
사용하되, APG 항목마다 별도 상태 머신이나 패키지가 있어야 한다고 해석하지 않는다.

## 해결

Bison을 제거하고 UI 패턴의 구조, 행동과 접근성 책임을 Coral로 통합한다. Coral은
먼저 네이티브 HTML로 요구사항을 충족할 수 있는지 확인하고, 재사용할 컴포넌트
계약이 실제로 필요할 때에만 Parts와 상태 및 동작을 제공한다. WAI-ARIA APG는
적용 가능한 패턴의 의미 구조, 키보드와 Focus 동작을 판단하는 기준으로 유지하지만,
그 목록을 Coral 컴포넌트나 상태 머신의 목록과 일대일로 대응시키지 않는다.

Bison의 Machine·Actor·Connect·Normalizer API와 프레임워크 Adapter는 Coral로
이름을 바꾸어 옮기지 않는다. Bison에서 확인한 네이티브 우선 원칙, 패턴별
접근성 조건과 실제 브라우저 검증 기준만 Coral의 작업 근거로 이전한다. Coral의
렌더러와 공개 API가 아직 정해지지 않았으므로 기존 구현을 억지로 보존하지 않고,
그 경계를 정한 뒤 컴포넌트 계층에서 다시 구현한다.

나중에 여러 실제 컴포넌트가 동일한 복잡한 전이 모델을 반복하고 독립된 행동
엔진이 이를 실질적으로 단순화한다는 근거가 생기면 좁은 상태 머신 계층이나 검증된
외부 구현을 다시 검토할 수 있다. 그때에도 APG 패턴이라는 이유만으로 상태 머신을
만들지 않고, 확인된 재사용 문제를 기준으로 범위를 정한다.
