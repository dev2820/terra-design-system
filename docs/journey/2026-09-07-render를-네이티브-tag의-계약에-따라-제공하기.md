# 2026-09-07 — render를 네이티브 Tag의 계약에 따라 제공하기

## 문제

Coral의 Part에 `render`를 제공하면 기본 요소를 다른 React 요소나 컴포넌트로
교체하면서 불필요한 Wrapper 없이 외부 컴포넌트와 합성할 수 있다. 모든 Part가
같은 API를 가지면 사용자가 기능의 유무를 따로 확인하지 않아도 된다는 장점도
있다.

그러나 Part의 기본 요소가 단순한 출력 형식이 아니라 의미와 동작의 근거인 경우가
있다. Fieldset을 검토하면서 `<fieldset>`은 하위 Form Control에 Disabled 상태를
전파하고, `<legend>`는 Fieldset의 이름과 Disabled 전파의 예외에 관여한다는 점이
드러났다. 이런 요소를 `div`나 동작을 알 수 없는 사용자 컴포넌트로 교체하면
ARIA 속성을 옮기는 것만으로 네이티브 계약을 복원할 수 없다. React의 컴포넌트
타입도 사용자 컴포넌트가 최종적으로 어떤 HTML Tag를 렌더링하고 전달받은 Props를
어떻게 적용하는지 보장하지 못한다.

따라서 모든 Part에 `render`를 일관되게 제공할지, 일부에만 제공한다면 무엇을
기준으로 경계를 정할지 결정해야 했다.

## 접근 방식

첫 번째 대안은 Base UI처럼 모든 Part에 넓은 `render` Escape Hatch를 제공하고,
대체 요소의 의미와 동작을 보존하는 책임을 사용자에게 맡기는 것이었다. 외부
컴포넌트나 다른 Coral 컴포넌트와 자유롭게 합성할 수 있고 API도 예측하기 쉽다.
반면 Coral이 Props와 Event를 병합하더라도 알 수 없는 컴포넌트가 이를 실제 DOM에
전달하는지는 보장할 수 없다. 네이티브 Form 동작, 키보드 조작, Focus와 Disabled
전파가 사라진 결과도 공개 API가 허용하게 되어, 접근성을 기본 조건으로 제공하는
Coral의 보장 범위가 모호해진다.

두 번째 대안은 `render`를 전혀 제공하지 않고 정해진 네이티브 요소만 렌더링하는
것이었다. 네이티브 계약과 검증 범위는 가장 분명하지만, 의미와 동작이 특정
Tag에 의존하지 않는 Part까지 외부 컴포넌트와 합성할 수 없게 한다. 실제 합성
요구가 생겼을 때 불필요한 Wrapper를 추가하거나 Coral을 우회해야 할 수 있다.

세 번째 대안은 네이티브 Tag가 Part의 핵심 계약을 소유하는지를 기준으로 삼고,
실제 필요가 확인된 경우에만 `render`를 제공하는 것이었다. 의미, Form 참여,
키보드와 Focus 동작, Disabled 전파 또는 구조적 관계가 네이티브 Tag 자체에서
성립한다면 다른 요소로 교체하는 순간 Coral이 같은 결과를 보장할 수 없으므로
`render`를 닫는다. 반대로 Coral이 Tag와 독립적으로 Props, Event와 ARIA를 통해
계약을 보존할 수 있는 Part는 구체적인 합성 요구와 대체 요소의 계약이 확인됐을
때 `render`를 열 수 있다.

`render`를 처음부터 넓게 제공한 뒤 제거하는 것은 호환성을 깨지만, 닫힌 API를
나중에 여는 것은 기능을 추가하는 변경이다. 아직 확인되지 않은 사용처를 위해
보장 범위를 넓히기보다 실제 사례가 생겼을 때 안전한 합성 계약을 정의하는 편이
Coral의 네이티브 우선 원칙과도 맞는다고 판단했다.

## 해결

Coral은 `render`를 모든 Part의 공통 기능으로 제공하지 않는다. Part의 핵심
계약을 네이티브 Tag가 소유하면 기본 요소를 교체했을 때 같은 의미와 동작을
Coral이 보장할 수 없으므로 `render`를 제공하지 않는다.

네이티브 Tag와 독립적으로 Coral이 계약을 보존할 수 있더라도 그것만으로
`render`를 자동으로 추가하지 않는다. 실제로 Wrapper 없는 합성이나 외부
컴포넌트 연결이 필요하다는 사용 사례가 확인되고, 대체 요소가 지켜야 할 접근성
계약을 공개 API와 테스트로 설명할 수 있을 때 해당 Part에만 추가한다.

이 결정은 현재 닫힌 확장 가능성을 영구히 금지하지 않는다. 이후 구체적인 필요가
생기면 `render`를 추가할 수 있으며, 그때에도 API의 일관성보다 네이티브 계약을
보존할 수 있는지가 우선 판단 기준이다. Coral이 제공하고 검증하는 기본 구성은
계속 네이티브 HTML의 의미와 동작을 유지한다.
