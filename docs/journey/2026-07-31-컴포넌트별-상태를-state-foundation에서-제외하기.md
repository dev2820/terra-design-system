# 2026-07-31 — 컴포넌트별 상태를 State Foundation에서 제외하기

## 문제

State Foundation의 공통 범위를 정하는 과정에서 `Readonly`, `Loading`,
`Invalid`처럼 특정한 컴포넌트나 작업에서만 필요한 상태까지 미리 정의할지
판단해야 했다. 이 상태들은 넓은 의미에서는 모두 State지만, 요소의 행동 가능성,
현재 상호작용, 입력 위치와 선택 여부를 나타내는 공통 네 축에 그대로 포함되지
않는다.

각 상태를 Foundation에 포함하면 제품과 컴포넌트 사이에서 같은 이름과 의미를
공유할 수 있다. 반면 실제 필요가 확인되지 않은 상태마다 별도의 축을 추가하면
Foundation의 공통 범위가 계속 커지고, 특정 컴포넌트의 조건을 모든 제품이
공유하는 규칙처럼 다루게 될 수 있었다.

## 접근 방식

한 가지 방법은 수정 가능성을 나타내는 Editability, 처리 진행 여부를 나타내는
Processing, 값의 유효성을 나타내는 Validation 같은 축을 Foundation에 함께
정의하는 것이었다. 이 방식은 관련 상태를 중앙에서 일관되게 설명할 수 있지만,
각 축은 일부 컴포넌트와 제품에만 필요하며 실제 적용 방식도 서로 다르다. 공통
필요가 확인되기 전에 축을 만들면 Terra가 아직 존재하지 않는 사용 사례를 위해
복잡성을 미리 소유하게 된다.

다른 방법은 여러 요소에서 공통으로 필요한 Availability, Interaction, Focus와
Selection만 Foundation에 남기고, 그 밖의 상태는 실제 의미와 동작을 소유하는
Recipe, Pattern 또는 제품에서 정의하는 것이었다. 이 방식은 같은 상태가 여러
곳에서 반복될 때까지 공통화를 미룬다는 한계가 있지만, Foundation이 특정
컴포넌트의 요구까지 미리 열거하지 않고 확인된 공통 계약에 집중할 수 있다.

확장 가능한 상태 목록을 Foundation에 미리 선언하는 방법도 검토했지만, 지역적인
상태를 추가하는 것은 공통 Foundation을 확장하는 일과 구분하는 편이 명확하다고
판단했다. 공통으로 제공하지 않는 상태가 필요하다는 이유만으로 Terra의 공통
State가 되는 것은 아니기 때문이다.

## 해결

State Foundation은 Availability, Interaction, Focus와 Selection의 네 축만
공통으로 정의한다. 특정 컴포넌트나 제품에 종속된 상태는 Foundation에 미리
포함하거나 공통 확장 상태로 열거하지 않는다.

그러한 상태가 필요하면 해당 의미와 동작을 소유한 Recipe, Pattern 또는 제품에서
정의한다. 여러 영역에서 동일한 의미와 계약이 반복되어 공통 상태로 다룰 근거가
확인되면 그때 Foundation의 범위를 다시 논의한다. 이를 통해 Terra는 확인된
공통성만 기반으로 제공하면서도 개별 제품이 필요한 상태를 만드는 일을 막지
않는다.
